# SVS-SERVER

The API of the voting system: FastAPI, async SQLModel on PostgreSQL, Redis. The project as a whole, how to run it and its security model are in the [main README](../README.md) and [docs/security.md](../docs/security.md); this is the map of the server.

```text
app/
  main.py               the application: routers under /api, the web client's page for every other path, middlewares
  config/env.py         the configuration; in production it refuses to start with a placeholder secret (see tests/test_env.py)
  routers/              auth, vote (cast, count, audit, bulletin board), users, admin (dashboard), candidates, bulletins
  models/               tables (user, vote, candidate, attributed_vote, bulletin) and the response models of the API
    voting_models.py    the ballot, the zero-knowledge proof and its verification
  utils/
    vote_utils.py       checking a ballot, the homomorphic count, the proof of decryption
    audit.py            checking an election from public data only (python -m app.utils.audit <server> <id>)
    ballot_maker.py     a voter in Python (the browser's side of the protocol), for the demo data and the tests
    auth_utils.py       hashes, tokens, one-time passwords; rate_limit.py (Redis)
  crons.py              counts the elections that are over, every minute
  db/                   engine and sessions; migrate.py (Alembic: adopt or upgrade, check); seed_demo.py (demo data with real ballots), seed*.py (random data for the interface)
  tests/                the tests: SQLite and an in-memory Redis, no service to start
migrations/             the history of the schema (Alembic); see migrations/README.md
openapi.json            generated by `make openapi`; the web client's SDK is generated from it (a test checks it is current)
```

## Commands

```bash
make install     # uv sync --dev: the server and the tools of the tests, as locked in uv.lock
make test        # pytest: the whole application on SQLite and fakeredis
make lint        # ruff check and format --check (what CI runs)
make format      # fix what can be fixed
make run-dev     # needs PostgreSQL and Redis (see .env.example), http://localhost:8000, docs at /docs
make seed-demo   # demo accounts and elections, with real ballots (does nothing if there is data)
make migrate     # bring the database to the latest schema; make migration m="..." writes one from a change of the models
make openapi     # rewrite openapi.json after a change to the API, then `bun run generate-API-CLIENT` in ../SVS-CLIENT
make deploy      # put the built web client in app/dist (the Docker image does this by itself)
```

## Things to know

- **The tests run the real application**, with election keys of 1024 bits (`PAILLIER_KEY_BITS`; production refuses less than 2048) so that making an election takes a tenth of a second instead of a second.
- **The admin dashboard uses PostgreSQL functions** (`to_char`, `date_trunc`): its routes are not covered by the SQLite tests.
- **Ballots are checked on a thread** (`asyncio.to_thread`): a ballot is a few exponentiations of 4096 bits per candidate.
- **The count is idempotent**: the cron, an administrator and several replicas may all run it; they write the same result.
- Dates are UTC with a timezone (`UTCDateTime`, the same column as before).
- The `vote_utils.get_vote_count` and the cron are the only places that use an election's private key.
